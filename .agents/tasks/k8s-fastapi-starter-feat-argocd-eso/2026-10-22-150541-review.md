# Argo CD GitOps + SOPS→Secrets Manager→ESO delivery model (v2)

This batch reverses the template's "deployment is a CI apply job" decision and adopts GitOps: two Argo CD `Application` CRs plus an ESO `ClusterSecretStore` in a new `deploy/argocd/` kustomization, a per-overlay `ExternalSecret` that materializes the existing `app-secrets` Secret from AWS Secrets Manager, a `sync-secrets` CI workflow that pushes SOPS-decrypted values to Secrets Manager, a daily `pg_dump` backup CronJob with its own IRSA ServiceAccount, and a `bootstrap_backups.py` provisioner for the S3 bucket + backup CMK. The old `deploy.yml` is deleted and migration ordering moves to an Argo CD PreSync hook. The whole change lands as the repo's first commits on `main`.

Watch for: nothing blocking. The single finding from the prior review pass — SPEC §7 still describing the deleted `deploy.yml` SHA-append migration flow — has been fixed (confirmed): §7 now describes the PreSync-hook lifecycle and names the removed workflow as gone. Two design deviations remain, both sound and documented: the vendored CRD schema filenames keep canonical kind casing because the pinned kubeconform 0.8.0 has no `toLower` template function (confirmed), and the kube-linter exclusions are `latest-tag` + `job-ttl-seconds-after-finished` rather than the SA-token check the design guessed (confirmed, both genuinely fire).

**Verdict**: APPROVED

## High-level view

The GitOps topology matches the design precisely. `deploy/argocd/` has no `namespace:` transformer, so the `ClusterSecretStore` renders cluster-scoped and un-namespaced (verified in the render); the dev `Application` auto-syncs (prune + selfHeal) while prod omits `automated` entirely but keeps `CreateNamespace=true`. The per-overlay `ExternalSecret` is named `app-secrets-external` with `target.name: app-secrets`, so `deployment.yaml`/`migration-job.yaml` keep resolving `secretRef: app-secrets` unchanged, and the old SOPS caveat blocks are gone from both overlays and the base kustomization.

The durable kubeconform gate works as intended. Pass (a) is lenient with `-ignore-missing-schemas`; pass (b) is scoped to the CRD-bearing renders with that flag removed and schema-location pointing only at the vendored directory. I verified pass (b) fails (exit 1) when a CRD schema is removed — the silent-skip regression this task exists to prevent is caught on every run, not by a human remembering a flag.

The write→read secrets contract is guarded in exactly one place — the `sync-secrets` key-shape check — and it is precise: it extracts only the value map (stringData or base64 data via mikefarah `@base64d`), validates the key set equals exactly `{DATABASE_URL, REDIS_URL}`, masks values, and uses put-first/create-on-404 with `InvalidRequestException` (scheduled-for-deletion) as a fatal case. AWS-mutating steps are gated to push-on-main so fork PRs stay dry-run.

The backup CronJob carries the load-bearing `app.kubernetes.io/name: k8s-fastapi-starter` label (NetworkPolicy selection) plus `app.kubernetes.io/component: backup`, uses a `backup` SA with `automountServiceAccountToken: true` for IRSA, and the any-IP egress rule gained 443 with a tightening-caveat comment. `BACKUP_PREFIX` defaults to `base` and each overlay patches it to `dev`/`prod` via a JSON-patch on the container's `env/0/value` — and the backup container's first env var is indeed `BACKUP_PREFIX`, so the patch index is correct. `bootstrap_backups.py` defaults to `--dry-run`, hard-errors on `--apply` with placeholder values, and defaults retention to 30 days.

ADR 0001 carries all three in-place edits (Decision summary updated, the "CI job not GitOps" bullet replaced, the self-contradictory "requires a new ADR" bullet amended to sanction in-place updates) plus a dated 2026-10-21 reversal note, with status kept "Accepted" and no new ADR created. SPEC §1/§2/§3/§6/§9/§10/§13 and the docs are updated; the ESO v0.10.0 floor, both documented rough edges, and the Reloader-as-future-not-added note are all present.

### Prior finding resolved: SPEC §7 migration ordering

The v1 review flagged that `SPEC.md` §7 still described the deleted `deploy.yml` SHA-append apply flow as the active ordering mechanism, contradicting §10/§13 and the rewritten `migration-job.yaml` comment. Commit `a24d873` fixed it: §7 now reads that the migration Job is an Argo CD PreSync hook (`sync-wave: "-1"`), that `hook-delete-policy: BeforeHookCreation` recreates a fresh Job each sync so the SHA-append dance is gone, that the removed `deploy.yml` apply workflow no longer exists, and that overlays still rename the Job per environment for identity. No remaining `deploy.yml` reference in SPEC survives except the two correct "has been removed" mentions in §7 and §10.

### Durable "resolves, not skips" kubeconform gate

Pass (b) is the load-bearing half of the gate, so I exercised the failure path rather than trusting the green run. With a schema directory missing `ExternalSecret_v1.json`, pass (b) reports `could not find schema for ExternalSecret` on the overlay render and exits 1. On the committed schemas the full `k8s-check` is green: pass (a) 22/22 valid 0 skipped, pass (b) 5 valid (Application×2, ClusterSecretStore×1, ExternalSecret×2) with 17 core kinds skipped via `-skip`. A missing, mis-named, or version-drifted vendored schema for any of the three kinds reddens the build every run, so the exact silent-skip regression this task exists to prevent is caught in CI, not by a human remembering to drop a flag.

The filename casing is a deliberate, documented deviation from the design's literal `{{ .ResourceKind | toLower }}` template. kubeconform 0.8.0 (the pinned CI version) has no `toLower` function, so the task uses `{{ .ResourceKind }}` verbatim and the vendored files carry canonical kind casing (`ExternalSecret_v1.json`, not `externalsecret_v1.json`). Both `pyproject.toml` and `crd-schemas/README.md` record the rationale, and matching canonical casing keeps resolution deterministic on case-sensitive Linux CI. This is the correct resolution of a design assumption that would not have worked as written.

### Secrets write→read contract

The `sync-secrets` extractor selects only the value map with `yq -o=json '.stringData // (.data | map_values(@base64d))'`, so `apiVersion`/`kind`/`metadata`/`type` never reach Secrets Manager. The key-set check compares `keys | sort` against the literal `["DATABASE_URL","REDIS_URL"]` and names any missing or extra key without printing values; values are `::add-mask::`'d first. Writes use `put-secret-value` first, fall back to `create-secret` only on `ResourceNotFoundException` (no pre-probe, TOCTOU-safe with the parallel dev/prod matrix), and treat `InvalidRequestException` (secret scheduled for deletion) as fatal with a `restore-secret` hint. AWS steps are gated on `github.event_name == 'push' && github.ref == 'refs/heads/main'`, so PRs and forks run the dry-run decrypt + validation only. The IAM comment lists `secretsmanager:PutSecretValue/CreateSecret/DescribeSecret` plus `RestoreSecret`; the last is strictly an operator action rather than a role permission the workflow exercises, but listing it in a comment is harmless and matches the error message's guidance.

### Backup CronJob egress, IRSA, and the per-env prefix patch

The backup pod template carries both `app.kubernetes.io/name: k8s-fastapi-starter` (the sole basis for the `app` NetworkPolicy selecting it) and `app.kubernetes.io/component: backup`. The any-IP egress rule in `networkpolicy.yaml` gained `443/TCP` with a reason comment (S3/STS/KMS/Secrets Manager), and the `TIGHTEN per environment` note now warns that any future `to:` selector must preserve the backup pod's egress to 5432 and 443 or backups silently fail. The `backup` SA sets `automountServiceAccountToken: true` (contrast the `app` SA's `false`) because IRSA needs the projected web-identity token for STS `AssumeRoleWithWebIdentity`. `BACKUP_PREFIX` is the backup container's first env var (`env/0`) with base value `base`, and each overlay patches `/spec/jobTemplate/spec/template/spec/containers/0/env/0/value` to `dev`/`prod` — the index matches, so dumps land under distinct `s3://…/dev/` and `s3://…/prod/` prefixes and never collide.

### kube-linter exclusions differ from the design's guess — both verified necessary

The design predicted the likely fire as `default-service-account`/token-automount on `automountServiceAccountToken: true` and said the result was "NOT pre-decided" — run the linter and add exclusions with written reasons for whatever actually fires. Running kube-linter 0.8.3 produces errors on the backup CronJob for `latest-tag` (the untagged `PLACEHOLDER_BACKUP_IMAGE`, which must stay a bare token pre-init) and `job-ttl-seconds-after-finished` (jobTemplate TTL interacting with the history limits). The SA-token check does not fire. Both exclusions are in `.kube-linter.yaml` with written reasons per SPEC §14.9, and the `k8s-check` task passes `--config deploy/k8s/.kube-linter.yaml`. With both exclusions in place, `kube-linter lint` on the dev/prod renders reports no errors.

### bootstrap_backups.py and its unit test

The script follows `check_sops_encrypted.py` conventions (module docstring, typed, `argparse`, `main(argv) -> int`), defaults to `--dry-run`, and hard-errors when `--apply` is combined with a still-`PLACEHOLDER_` bucket/key/alias/region. `boto3` and `boto3-stubs[kms,s3]` are dev deps (so `mypy --strict` resolves the client stubs without `Any`); the single `cast` on the S3 `LocationConstraint` is justified inline against the closed-Literal stub. `test_bootstrap_backups.py` covers the dry-run default, the mutually-exclusive flags, valid/invalid bucket names, the placeholder guard under `--apply`, empty-region rejection, non-positive retention rejection, and asserts the deterministic 30-day plan line — all 39 unit tests pass with no services.

### Verification gates

`uv run poe k8s-check` is green (both kubeconform passes + kube-linter), and `kubectl kustomize deploy/argocd` emits the `ClusterSecretStore` with no `metadata.namespace`. `uv run poe docs-build` (`mkdocs build --strict`) passes. Unit tests (39) pass; the three failing tests under `poe check` are the `@pytest.mark.integration` API tests that need a live Postgres (`role "app" does not exist`), out of scope for template CI. `poe security`'s only failure is the absence of the `gitleaks` binary locally — an environment gap, not a repo defect; the SOPS plaintext guard and ruff `S` rules both pass, and no plaintext secret material is committed (only placeholder `secrets.example.yaml`, the zero-material ExternalSecrets, and the credential-free ClusterSecretStore). `rg PLACEHOLDER_` lists exactly the 13 registered tokens. Both workflow YAMLs parse. All six commits are Conventional Commits.
