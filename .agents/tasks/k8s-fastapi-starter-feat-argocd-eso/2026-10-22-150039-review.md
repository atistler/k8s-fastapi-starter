# Argo CD GitOps + SOPS→Secrets Manager→ESO delivery model

This batch reverses the template's "deployment is a CI apply job" decision and adopts GitOps: two Argo CD `Application` CRs plus an ESO `ClusterSecretStore` in a new `deploy/argocd/` kustomization, a per-overlay `ExternalSecret` that materializes the existing `app-secrets` Secret from AWS Secrets Manager, a `sync-secrets` CI workflow that pushes SOPS-decrypted values to Secrets Manager, a daily `pg_dump` backup CronJob with its own IRSA ServiceAccount, and a `bootstrap_backups.py` provisioner for the S3 bucket + backup CMK. The old `deploy.yml` is deleted and migration ordering moves to an Argo CD PreSync hook. The whole change lands as the repo's first commits on `main`.

Watch for: a stale paragraph in `SPEC.md` §7 still describes the deleted `deploy.yml` SHA-append migration flow as the active mechanism, contradicting §10/§13 and the rewritten migration-Job comment (confirmed). Two design deviations are both sound and documented: CRD schema filenames keep canonical kind casing because the pinned kubeconform 0.8.0 has no `toLower` template function (confirmed), and the kube-linter exclusions are `latest-tag` + `job-ttl-seconds-after-finished` rather than the SA-token check the design guessed (confirmed, both genuinely fire).

**Verdict**: NEEDS_CHANGES

## High-level view

The GitOps topology matches the design precisely. `deploy/argocd/` has no `namespace:` transformer, so the `ClusterSecretStore` renders cluster-scoped and un-namespaced (verified in the render); the dev `Application` auto-syncs while prod omits `automated` entirely but keeps `CreateNamespace=true`. The per-overlay `ExternalSecret` is named `app-secrets-external` with `target.name: app-secrets`, so `deployment.yaml`/`migration-job.yaml` keep resolving `secretRef: app-secrets` unchanged, and the old SOPS caveat blocks are gone from both overlays and the base kustomization.

The durable kubeconform gate works as intended. Pass (a) is lenient with `-ignore-missing-schemas`; pass (b) is scoped to the CRD-bearing renders with that flag removed and schema-location pointing only at the vendored directory. I verified pass (b) fails (exit 1) when a CRD schema is removed — the silent-skip regression this task exists to prevent is caught on every run, not by a human remembering a flag.

The write→read secrets contract is guarded in exactly one place — the `sync-secrets` key-shape check — and it is precise: it extracts only the value map (stringData or base64 data via mikefarah `@base64d`), validates the key set equals exactly `{DATABASE_URL, REDIS_URL}`, masks values, and uses put-first/create-on-404 with `InvalidRequestException` (scheduled-for-deletion) as a fatal case. AWS-mutating steps are gated to push-on-main so fork PRs stay dry-run.

The backup CronJob carries the load-bearing `app.kubernetes.io/name: k8s-fastapi-starter` label (NetworkPolicy selection), uses a `backup` SA with `automountServiceAccountToken: true` for IRSA, and the any-IP egress rule gained 443 with a tightening-caveat comment. `bootstrap_backups.py` defaults to `--dry-run`, hard-errors on `--apply` with placeholder values, and defaults retention to 30 days.

The one gap is documentation consistency: SPEC §7 was not updated to match the new PreSync-hook ordering and still references the deleted `deploy.yml`, leaving the authoritative spec self-contradictory about a core behavior this batch changed.

### Durable "resolves, not skips" kubeconform gate

Pass (b) is the load-bearing half of the gate, so I exercised the failure path rather than trusting the green run. With a schema directory missing `ExternalSecret_v1.json`, pass (b) reports `could not find schema for ExternalSecret` on both overlay renders and exits 1. On the committed schemas the full `k8s-check` is green: pass (a) 22/22 valid 0 skipped, pass (b) 5 valid (Application×2, ClusterSecretStore×1, ExternalSecret×2) with 17 core kinds skipped via `-skip`. A missing, mis-named, or version-drifted vendored schema for any of the three kinds reddens the build every run.

The filename casing is a deliberate, documented deviation from the design's literal `{{ .ResourceKind | toLower }}` template. kubeconform 0.8.0 (the pinned CI version) has no `toLower` function, so the task uses `{{ .ResourceKind }}` verbatim and the vendored files carry canonical kind casing (`ExternalSecret_v1.json`, not `externalsecret_v1.json`). Both `pyproject.toml` and `crd-schemas/README.md` record the rationale, and matching canonical casing keeps resolution deterministic on case-sensitive Linux CI. This is the correct resolution of a design assumption that would not have worked as written.

### Secrets write→read contract

The `sync-secrets` extractor selects only the value map with `yq -o=json '.stringData // (.data | map_values(@base64d))'`, so `apiVersion`/`kind`/`metadata`/`type` never reach Secrets Manager. The key-set check compares `keys | sort` against the literal `["DATABASE_URL","REDIS_URL"]` and names any missing or extra key without printing values; values are `::add-mask::`'d first. Writes use `put-secret-value` first, fall back to `create-secret` only on `ResourceNotFoundException` (no pre-probe, TOCTOU-safe with the parallel dev/prod matrix), and treat `InvalidRequestException` (secret scheduled for deletion) as fatal with a `restore-secret` hint. AWS steps are gated on `github.event_name == 'push' && github.ref == 'refs/heads/main'`, so PRs and forks run the dry-run decrypt + validation only. The IAM comment lists `secretsmanager:PutSecretValue/CreateSecret/DescribeSecret` plus `RestoreSecret`; the last is strictly an operator action rather than a role permission the workflow exercises, but listing it in a comment is harmless and matches the error message's guidance.

### Backup CronJob egress and IRSA

The backup pod template carries both `app.kubernetes.io/name: k8s-fastapi-starter` (the sole basis for the `app` NetworkPolicy selecting it) and `app.kubernetes.io/component: backup`. The any-IP egress rule in `networkpolicy.yaml` gained `443/TCP` with a reason comment (S3/STS/KMS/Secrets Manager), and the `TIGHTEN per environment` note now warns that any future `to:` selector must preserve the backup pod's egress to 5432 and 443 or backups silently fail. The `backup` SA sets `automountServiceAccountToken: true` (contrast the `app` SA's `false`) because IRSA needs the projected web-identity token for STS `AssumeRoleWithWebIdentity`. The `BACKUP_PREFIX` base value is `base` and each overlay patches it to `dev`/`prod` via a JSON-patch on the CronJob container env, so dumps never collide under the bucket.

### kube-linter exclusions differ from the design's guess — both verified necessary

The design predicted the likely fire as `default-service-account`/token-automount on `automountServiceAccountToken: true` and said the result was "NOT pre-decided" — run the linter and add exclusions with written reasons for whatever actually fires. Running kube-linter 0.8.3 with no exclusions produces 4 errors, all on the backup CronJob: `latest-tag` (the untagged `PLACEHOLDER_BACKUP_IMAGE`, which must stay a bare token pre-init) and `job-ttl-seconds-after-finished` (jobTemplate TTL interacting with the history limits). The SA-token check does not fire. Both exclusions are in `.kube-linter.yaml` with written reasons per SPEC §14.9, and the `k8s-check` task passes `--config deploy/k8s/.kube-linter.yaml`. This is the design's instruction followed correctly against the real linter output.

### SPEC §7 stale migration ordering

`SPEC.md` §10 and §13 correctly describe Argo CD GitOps with the migration-Job-before-Deployment ordering as a PreSync hook, and `migration-job.yaml`'s rewritten header comment states the SHA-append dance is gone. But §7's Kubernetes bullet still reads: "CD (`deploy.yml`) appends the commit SHA at apply time, excluding the base-named Job from the final apply, so reruns do not collide." That names a deleted workflow and an abandoned mechanism, leaving the authoritative spec internally inconsistent about one of the central behaviors this batch changes. context.json flags "§7 migration ordering" as a relevant area, so this is in scope even though the files-to-modify table enumerated only §1/§2/§3/§6/§9/§10/§13.
